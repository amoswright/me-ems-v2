# Summary tab — step summary style guide

Summaries are written by hand (a Claude Code session reasoning over each step directly), not
generated by `scripts/generate_summaries.py` — that script calls the Anthropic API, which costs
money per call. It's kept in the repo for reference on the original label/detail conventions but
should not be run. Do not add a replacement API-based script either; this is deliberately a slow,
one-protocol-at-a-time human-reviewed process.

## Where summaries live

`step.summary = { label, detail?, category? }` on each `ProtocolStep`, and the same on
`ProtocolIntroItem` (for non-PEARLS intro content worth summarizing — PEARLS boxes always render
full text in the Summary tab already and don't take a summary). Written directly into
`public/data/protocols/{category}.json`. No `import.py` rerun needed — summaries are additive to
the already-imported step data, not part of the import pipeline.

## Category (drives the Summary tab icon)

Every summary should set `category` to one of six values. This is what selects the icon in
`CategoryIcon` (`src/components/ProtocolSummaryView.tsx`) — set explicitly by you, not guessed
from the step text, so two steps that describe the same kind of action always get the same icon
even if worded completely differently. Leaving `category` off falls back to the older
text-regex-guessed icon, which is inconsistent — always set it.

| category | means | examples |
|---|---|---|
| `medication` | anything administered to the patient with a dose/route | drugs, O2, IV fluids, nebulized treatments |
| `procedure` | a physical skill or device applied to the patient | IV/IO access, intubation, BVM ventilation, CPAP application, CPR, defibrillation, hemorrhage control, spinal immobilization, airway management |
| `assessment` | gathering information | vitals, cardiac monitor, 12-lead ECG, GCS, blood glucose check, pain scale, reassessment |
| `communication` | talking to someone outside the patient | request ALS, contact OLMC, notify/alert hospital, transport |
| `decision` | a conditional/branch point with no direct patient action of its own | "if X, consider Y", multi-option branches |
| (none) | steps that don't fit cleanly, or where guessing would be worse than no icon | — |

The line between `medication` and `procedure` is the one to get right: if the step's core
content is a dose or route (even for something like O2 or a fluid bolus), it's `medication`.
If it's a technique or device with no dose to report, it's `procedure` — including cases where
the technique's purpose is to deliver O2 (BVM, CPAP), since the step itself has no dose/route to
show.

## Before writing a protocol's summaries: check canonical-steps.json

`docs/summary-project/canonical-steps.json` is a lookup of normalized step text → an already-
decided `{ label, detail? }`. ~18% of all steps are exact or near-duplicates of a step that
appears elsewhere ("Request ALS", "Cardiac monitor", "O₂ as appropriate", "Establish IV en
route", ...) — reuse the canonical entry verbatim rather than re-wording it slightly differently
each time. Consistency here matters more than any individual phrasing choice: a clinician
scanning ten protocols should see the same step described the same way every time.

If a step in the current protocol matches (or nearly matches) an existing canonical entry, use
it as-is. If you write a new label for a generic action that's likely to recur, add it to
canonical-steps.json in the same pass.

## Label

- 2-5 words, the core action, no trailing punctuation.
- Plain drug names in normal case except standard ALL-CAPS convention for the "changed syllable"
  in generic names already used throughout this corpus (EPINEPHrine, NOREPInephrine) — match
  what the protocol text already does, don't invent new capitalization.
- Good: "Request ALS", "Epinephrine IM", "Cardiac Monitor", "Dexamethasone", "CPAP — Severe
  Bronchospasm".
- Bad: full sentences, trailing periods, restating the step number or provider level.

## Detail

- 1-3 short lines, plain text (no HTML).
- Omit entirely (no `detail` key) if the label already says everything — most non-medication
  steps ("Cardiac monitor", "Request ALS") need no detail at all.
- For medication steps, use the Adult/Peds line format below — the UI parses these lines
  specifically and renders them as colored badges. This is the most important formatting rule
  in this guide; deviating from it silently degrades to plain text.
- For decision/conditional steps: state the trigger and the action plainly, no HTML.
- Abbreviate routes as: IV, IM, IO, PO, IN, SL, SQ, NEB, ET. Use × for "times" (×2, ×3), →
  for "then", ≤ ≥ for comparisons.
- Weight-based doses: `0.6 mg/kg (max 16 mg)`.
- Max line length ~60 chars.

### Medication detail line format (drives the dose badges)

The renderer (`MedDetailLine` in `src/components/ProtocolSummaryView.tsx`) looks for these
patterns, one per line in `detail`:

```
Adult: <dose text, include the route abbreviation>
Peds <25kg: <dose text, include route>
Peds ≥25kg: <dose text, include route>
<Drug/context label>: <dose text, include route>
```

Example (EPINEPHrine, severe bronchospasm):

```
Adult: 0.3 mg IM
Peds <25kg: 0.15 mg IM · ≥25kg: 0.3 mg IM
```

Any route abbreviation appearing in a detail line (IV, IM, IO, PO, IN, SL, SQ, NEB, ET, or a
compound like IV/IO) is automatically wrapped in a colored badge — do not add markup yourself,
just include the plain abbreviation as a word in the text.

### Route color legend (fixed across the whole app — don't improvise new colors per protocol)

| Route | Color |
|---|---|
| IV | blue |
| IM | purple |
| IO | red |
| PO | green |
| IN | teal |
| SL | amber |
| SQ | pink |
| NEB | indigo |
| ET | slate (neutral) |
| compound (IV/IO, IM/IO, IV/IM/IO) | slate (neutral — it's a choice of site, not one route) |

Pictogram route icons (`public/assets/route-icons/*.svg`, shown via `RouteIconStack`) are a
fallback for steps that have no curated summary yet. Once a step gets a `summary.detail` in the
Adult/Peds line format, the badge rendering takes over automatically — no need to touch the
fallback icons.

## Accuracy over speed

This is medical content. When a step's dosing is ambiguous, cross-check against the "Original"
tab (the actual rendered PDF page) before writing the detail line, not just the extracted
`step.html`. If still uncertain, leave `detail` off rather than guess — a missing detail line is
harmless, a wrong one is not.

## Workflow per protocol

1. Open `docs/summary-project/PROGRESS.md`, pick the next `pending` row (front-to-back document
   order).
2. Read every step's `html` for that protocol (all provider levels), plus any PEARLS intro items.
3. For each step: check canonical-steps.json first; otherwise write a new label (+ detail if
   warranted, following the medication format for dose steps).
4. Write the `summary` object directly into the protocol's JSON file.
5. If you introduced a new reusable canonical step, add it to canonical-steps.json.
6. Verify in the browser (Summary tab) — check badges render, nothing looks truncated or wrong.
7. Update the row's status in PROGRESS.md to `done`, bump the total-done count at the top.
8. Commit summary + progress-file changes together.
